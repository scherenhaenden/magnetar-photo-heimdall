# User feature progress

This is the delivery-status view of Heimdall's user-facing product. It is intentionally more atomic than the feature specifications: a row represents one observable user outcome, not a whole technical module.

**Status definitions:** **Implemented** means the current application or its shipped services perform the behavior end-to-end within the stated boundary. **Preview only** means the desktop surface is visible but intentionally has no connected operational backend. **Planned** means it is specified but not available in the application. A feature never becomes implemented merely because a contract, mock-looking display value, or design screen exists.

| Library registration | Choose a folder using the native folder picker | **Implemented** | The user can select a local folder instead of typing its path. | The picker is unavailable in headless test environments; no remote picker exists. | Reuse the picker workflow for library editing. |

| Library registration | Register a local folder as a library | **Implemented** | The folder is stored as a library root in SQLite. | It only registers a local reachable directory; removable-drive identity and permissions diagnostics are not yet surfaced. | Display the persisted root list and root status. |
| Library registration | Prevent duplicate roots | **Implemented** | SQLite enforces a unique canonical path for a registered root. | The UI does not yet turn this database error into a tailored duplicate-root message. | Present an actionable duplicate-root result. |
| Library registration | Register a macOS mounted volume | **Implemented** | A mounted volume works when it is visible to the local filesystem and selected as a folder. | Heimdall does not yet detect mount lifecycle, volume identity, or reconnection. | Add mount discovery and unavailable-root status. |

| Scanning | Start a scan after adding a library | **Implemented** | Add and scan registers the root, scans it, and displays catalogued media count on success. | The current scan is local, foreground-oriented, and has no resume queue. | Add job persistence, pause, resume, and scan history. |
| Scanning | Scan subfolders recursively | **Implemented** | The local scanner enumerates files beneath the selected root. | Access-denied and per-file failures are not yet modeled as user-visible scan diagnostics. | Capture and show skipped paths, errors, and retry controls. |
| Scanning | Detect JPEG files | **Implemented** | `.jpg` and `.jpeg` files are catalogued. | The scan records file path, length, and mtime; it does not yet persist media analysis results. | Attach capture-date and hash persistence to scan results. |
| Scanning | Detect PNG files | **Implemented** | `.png` files are catalogued. | PNG capture-date handling depends on later metadata persistence. | Persist available PNG/XMP metadata evidence. |
| Scanning | Detect HEIC files | **Implemented** | `.heic` files are selected by the scanner. | Successful metadata extraction can vary with the source file/library support and is not yet connected to the catalog. | Record parse outcome and metadata provenance per asset. |
| Scanning | Detect TIFF files | **Implemented** | `.tif` and `.tiff` files are selected by the scanner. | No thumbnail or browser preview is connected. | Generate safe derivatives after a scan. |
| Scanning | Detect RAW files | **Implemented** | `.dng`, `.nef`, `.cr2`, `.arw`, and `.raf` are selected by the scanner. | RAW decoding, previews, and sidecar pairing are not implemented. | Add RAW capability detection and derivative pipeline. |
| Scanning | Detect video files | **Implemented** | `.mp4` and `.mov` files are selected by the scanner. | Video duration, preview, and playback are not implemented. | Persist video metadata and create safe preview support. |
| Scanning | Ignore unsupported file extensions | **Implemented** | Files outside the explicit supported extension list are skipped. | The user cannot yet configure extensions or see the skipped-type summary. | Add a scan report with configured type rules. |
| Catalogue | Persist a registered library | **Implemented** | Library id, display name, canonical path, and registration time are stored in SQLite. | There is no UI list of saved libraries yet. | Connect the Libraries screen to real catalog queries. |
| Catalogue | Persist discovered media entries | **Implemented** | Each discovered item is stored with relative path, length, and filesystem last-write time. | Media records do not yet include metadata, hashes, thumbnails, or operation history. | Extend the database schema through the DataAccess.Database sublayer. |
| Catalogue | Re-scan without creating a second row for the same relative path | **Implemented** | A scan upserts an existing library/path pair instead of duplicating it. | Deleted source files are not yet reconciled out of the catalogue. | Add missing-file reconciliation and a user-visible state. |
| Capture dates | Read EXIF DateTimeOriginal | **Implemented (service)** | The media-analysis service resolves the camera capture date from EXIF where present. | The result is not yet shown or persisted by the desktop catalog flow. | Store and display the resolved date and its source. |
| Capture dates | Read XMP capture date | **Implemented (service)** | The resolver checks standard XMP creation/date-original fields after EXIF. | It is not yet surfaced in the application. | Persist XMP evidence and display it in asset details. |
| Capture dates | Read QuickTime creation date | **Implemented (service)** | The resolver checks QuickTime metadata and a movie-header fallback for compatible videos. | It is not yet wired to video records in the catalogue. | Run the resolver during video analysis and retain provenance. |
| Capture dates | Fall back to filesystem modification time | **Implemented (service)** | When no usable embedded date exists, the resolver returns filesystem mtime. | This is explicitly low confidence and does not prove the camera capture time. | Label low-confidence dates in the browser and let users correct them. |
| Capture dates | See date source and confidence | **Planned** | No asset-details screen exposes EXIF/XMP/QuickTime/mtime provenance yet. | The service has the evidence, but the user cannot inspect it. | Persist all evidence and add source/confidence badges. |
| Duplicate analysis | Compute a full BLAKE3 content hash | **Implemented (service)** | The hasher streams the whole file and returns a BLAKE3 digest. | It is not scheduled by the desktop scan and results are not stored. | Add a catalog analysis job and hash columns/indexes. |
| Duplicate analysis | Compute a fast versioned fingerprint | **Implemented (service)** | The hasher calculates a BLAKE3 fingerprint using file length plus first/last 1 MiB windows. | It is a pre-filter, not proof of duplication; no UI exposes it yet. | Use it to group candidates before a full-hash confirmation. |
| Duplicate analysis | Hash large files without loading them all into RAM | **Implemented (service)** | Hashing uses streaming 128 KiB reads. | It has no thermal/workload scheduling connection yet. | Run it through a throttled analysis queue. |
| Duplicate analysis | View duplicate groups | **Preview only** | A duplicate-review screen can be opened from the desktop preview buttons. | The displayed information is presentation-only; it is not backed by BLAKE3 groups. | Connect real candidate groups and full-hash confirmation. |
| Duplicate analysis | Choose which duplicate to keep | **Preview only** | The duplicate decision surface communicates the intended review workflow. | It cannot delete, move, quarantine, or record a real choice. | Add persisted review decisions and a generated operation plan. |
| Library exploration | Open an asset-exploration screen | **Preview only** | An Explore library preview is reachable from the start screen. | It does not load the SQLite catalogue or media files. | Bind real library queries, filters, and thumbnails. |
| Library exploration | Filter/search a library | **Planned** | No operational search or filtering is connected. | Search-like controls in the shell are visual only. | Add indexed catalogue queries and filter state. |
| Library summary | Open a library summary | **Preview only** | A Summary preview is reachable from the start screen. | Its values are presentation data, not live telemetry. | Populate it from persisted scan, analysis, and operation data. |
| Library list | Open a libraries screen | **Preview only** | A Libraries preview is reachable from the start screen. | It does not enumerate, edit, or remove stored roots. | Bind it to the SQLite library-root list. |
| Organization | Open an organization workflow | **Preview only** | An Organize preview communicates the proposed workflow. | No filesystem mutation can occur from the screen. | Add rule editing and plan generation. |
| Organization | Preview a file operation plan | **Preview only** | A Review plan preview is available. | No real plan, conflict check, or approval state is connected. | Generate deterministic, reviewable operations from catalogued assets. |
| Organization | Apply approved rename/move/copy operations | **Planned** | No organization operation changes a source file. | This is deliberately unavailable until review, journal, verification, quarantine, and undo exist. | Implement a transactional operation executor with recovery. |
| File naming | Configure date-based destination folders | **Planned** | No UI or rule engine currently creates dated paths. | Existing feature docs are specifications only. | Add a validated destination-template editor. |
| File naming | Configure filenames such as `yyyy-MM-dd-HH-mm-sss-md5hash` | **Planned** | No configurable filename formatter exists yet. | The MD5 example is not the planned identity mechanism. | Support tokens, escaped literals, collision policy, and dry-run previews. |
| File naming | Use BLAKE3 instead of MD5 for duplicate identity | **Implemented (service)** | BLAKE3 hashing is available to the product core. | Naming templates cannot yet consume the hash, and a content hash is not persisted. | Expose an explicit BLAKE3 token only after hash lifecycle is defined. |
| File naming | Resolve naming collisions | **Planned** | No rename plan or collision resolver is present. | Heimdall does not rename source files today. | Provide deterministic suffixing and a visible collision report. |
| Previews | Preview photos safely | **Planned** | No thumbnail/image decode pipeline is connected. | The existing screens are UI composition, not media previews. | Generate cached read-only derivatives. |
| Previews | Preview RAW media | **Planned** | No RAW renderer or embedded-preview extractor is available. | RAW files may be catalogued but not visually inspected. | Add a pluggable RAW preview service. |
| Previews | Preview video media | **Planned** | No video thumbnail or playback facility is available. | Video files may be catalogued only. | Add a platform-safe video preview strategy. |
| Remote work | Discover remote-agent capabilities | **Implemented (contract)** | Typed v1 RPC contracts describe roots, operations, concurrency, sensors, and receipt support. | There is no SSH transport/client or deployable remote agent yet. | Implement authenticated transport and a real agent (C# and/or Python). |
| Remote work | Submit an SSH remote scan/hash/preview/export/transfer job | **Planned** | No user can submit work over SSH today. | Contracts deliberately prohibit arbitrary remote shell text. | Build an SSH transport that carries typed requests to an allowlisted remote agent. |
| Remote work | Run the remote agent in Python | **Planned** | Python is an accepted implementation option, but no Python agent is included. | The C# contracts do not require a C# server implementation. | Define wire serialization and ship a version-compatible Python agent. |
| Remote work | Restrict a remote job to an approved root | **Implemented (contract)** | Requests validate an opaque allowed root id before work is accepted. | Enforcement by a concrete remote server is still pending. | Enforce canonical-path containment in the server implementation. |
| Remote work | Reject path traversal in remote requests | **Implemented (contract)** | Absolute paths, drive-qualified paths, backslashes, null bytes, empty segments, `.` and `..` are rejected. | No network endpoint applies this yet. | Test the same validation at the remote-agent boundary. |
| Remote work | Recover a remote job after disconnect | **Implemented (contract)** | The protocol defines idempotency keys and durable operation receipts. | No transport or durable server receipt store exists yet. | Implement receipt persistence and client retry UX. |
| Thermal workload | Classify a local or remote temperature reading | **Implemented (contract/service)** | The thermal controller classifies normal, warning, high, critical, and unavailable readings. | No actual platform sensor provider or desktop status display is connected. | Add OS-specific sensor adapters and a live status indicator. |
| Thermal workload | Reduce concurrency at warning temperature | **Implemented (service)** | A valid warning snapshot yields the policy's reduced concurrency. | It is not yet connected to scan/hash workers. | Apply decisions to real job schedulers. |
| Thermal workload | Pause new heavy work at high temperature | **Implemented (service)** | A valid high snapshot rejects new work and yields the high concurrency setting for existing control. | It does not stop a real job because no scheduler consumes it yet. | Connect pause/admission control to local and remote queues. |
| Thermal workload | Stop work at critical temperature | **Implemented (service)** | Critical readings produce zero concurrency and reject new work. | The current service is a pure controller; no process is stopped automatically. | Implement cooperative cancellation/checkpoints for active jobs. |
| Thermal workload | Avoid restarting too early after overheating | **Implemented (service)** | Cooling hysteresis and a minimum safe duration keep work blocked until the policy is satisfied. | Only effective once callers observe sensors continuously. | Persist/observe controller state through the workload coordinator. |
| Thermal workload | Handle unavailable or stale temperature telemetry safely | **Implemented (service)** | Missing, stale, future-dated, or invalid readings block new work rather than inventing a temperature. | The UI does not explain this state yet. | Present a clear sensor-unavailable/cooling reason to the user. |
| Export | Export resized copies | **Planned** | No export pipeline is runnable. | Original files are not copied or modified by an export action today. | Implement a plan-first export job with verification. |
| Export | Apply a watermark during export | **Planned** | No watermark editor or renderer is available. | No original or derivative is currently changed. | Add previewable watermark settings within export plans. |
| Backup | Create a backup/mirror of a library | **Planned** | No backup or mirroring process is available. | No target is written by Heimdall today. | Implement verified copy, journal, and resume behavior. |
| Library health | Diagnose missing/corrupt/inconsistent library items | **Planned** | No health-report job is exposed. | Scan errors and catalog reconciliation are still minimal. | Add health checks with non-destructive repair proposals. |
| Safety | Open preview surfaces without changing any media file | **Implemented** | All current explore, duplicate, organize, review-plan, summary, and libraries preview actions are non-mutating. | They are not substitutes for implemented workflows. | Keep no-op behavior until each workflow has review and approval semantics. |
| Safety | Permanently delete an original | **Not available by design** | Heimdall has no delete command in the current app. | Permanent deletion is prohibited for the first release design. | If ever proposed, require explicit post-quarantine policy and recovery guarantees. |
| Safety | Review, approve, journal, quarantine, and undo an operation | **Planned** | No operational plan lifecycle is implemented. | This is a prerequisite for every future filesystem-changing feature. | Build immutable journal records, verified execution, quarantine, and undo before enabling mutations. |

## Evidence boundary

The **Implemented (service)** and **Implemented (contract)** labels mean tested code is present below the current desktop workflow, not that the user can trigger it from every screen. The distinction is deliberate: it prevents the design previews from overstating the product's current operational capability.

The feature specifications in [features](features/README.md) define the desired complete product. This table is the shorter, status-oriented companion for deciding the next deliverable.
